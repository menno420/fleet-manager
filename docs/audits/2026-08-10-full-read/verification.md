# Coverage verification — fleet-manager full-read audit

> **Status:** `audit`

The acceptance test for this audit was: *every path in `git ls-files` appears in the
ledger, and the ledger is built from what the readers returned rather than from what
they claimed*. This file records the mechanical result.

## The denominator

`enumeration.tsv` froze `git ls-files` at `4b59e9b` before any file was read: **833 paths,
30,006,142 bytes**. It is not regenerated by any later stage, so the set cannot be
narrowed to whatever happened to get covered.

## Result

| | count |
|---|---|
| paths enumerated | 833 |
| **READ** — returned and fingerprint reproduced | **833** |
| UNVERIFIED — returned but fingerprint did not reproduce | 0 |
| NO-RETURN — no agent returned this path | 0 |

Read modes: **814 full**, **19 structural**.

## How a row earned `READ`

Each read agent returned, per path, three content-derived values: the total line count,
the first 60 characters of the first non-empty line, and the last 60 characters of the
last non-empty line. Every one was recomputed from the working tree and compared; a path
needed at least two of the three to match before its row was written `READ`. The line
count alone is not sufficient and the head slice alone is not sufficient, because either
could be produced by a `wc -l` or a `head` without opening the file.

This is the part that makes the coverage claim checkable rather than assertable. An agent
that skipped a file could still list its path; it could not produce that file's last
non-empty line.

## Structural reads, and why they are recorded separately

Nineteen files hold 22,073,427 of the 30,006,142 bytes and are vendored or machine-
generated: the sixteen `.substrate/backup/bootstrap-*.py` kit snapshots, `bootstrap.py`,
`.substrate/guard-fires.jsonl` (an append-only telemetry log) and
`telemetry/triggers-snapshot.json`. These were opened and read for provenance, version
banner, schema and anomalies rather than line by line, and carry `structural` in the
ledger. Recording that honestly is the point of the distinction: a ledger claiming a
token-by-token read of a 5.5 MB append-only log would be an instance of the exact defect
this audit was commissioned to find.

## One file could not be fully fingerprinted, and that is recorded here

`.substrate/guard-fires.jsonl` is append-only telemetry that this repository writes on
every `bootstrap.py check --strict` run — including the runs this audit itself made. It
grew from 9,811 to 9,820+ lines while the audit was in progress, so its line count and
last non-empty line provably cannot reproduce. Only its head is stable, so only its head
was checked, and its ledger row says `structural`.

This is stated rather than quietly tolerated. A moving target must not be scored as an
unread file, and it must not be scored as a clean verification either. A read agent
predicted this failure mode before it occurred, in its return for batch b22.
