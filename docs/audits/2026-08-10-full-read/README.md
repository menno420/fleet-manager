# Full-read audit — fleet-manager, 2026-08-10

> **Status:** `audit`

Every tracked file in this repository, read and accounted for. Not a sample, not
the read path, not "the important ones".

## Why this exists

Five consecutive sessions whose stated job was to read this repo and put it in
order each missed that the owner's current plan was unreachable from the front
door. Each of those sessions read a coherent subset, and coherence is what gets
checked. The instruction that produced this audit was literal: *"it should read
every file in the fleet manager repo. and not nearly every file... I mean every
file 100%"*.

## The method, and what makes the coverage claim checkable

1. **Enumerate first.** The denominator is committed before any file is read, so
   the set cannot be quietly narrowed to whatever got covered.
2. **Fan out.** Read agents receive explicit path lists, ~20–30 files each,
   batched by cumulative bytes so no agent is handed more than it can hold.
3. **Return, don't claim.** Each agent returns, per path, a content-derived
   fingerprint: total line count, the first 60 characters of the first non-empty
   line, and the last 60 characters of the last non-empty line. A batch-level
   "covered" assertion is not accepted as evidence and is not recorded.
4. **Re-check mechanically.** Every returned fingerprint is recomputed from the
   working tree and compared. A path whose fingerprint does not reproduce is
   treated as unread and re-dispatched, not argued about.
5. **Diff.** Ledger against enumeration. A path in the enumeration and absent
   from the ledger is a failure of the task, recorded as such.

### Read modes

`full` and `structural` are both recorded, and the distinction is not cosmetic.
Nineteen files carry 22,073,427 of the repository's 30,006,142 bytes and are
machine-generated or vendored: the sixteen `.substrate/backup/bootstrap-*.py`
kit snapshots, `bootstrap.py` itself, `.substrate/guard-fires.jsonl` (an
append-only telemetry log) and `telemetry/triggers-snapshot.json`. These are
opened and read for structure, provenance, banner, schema and anomalies rather
than line by line, and the ledger says `structural` against each with the reason.
Recording that honestly is the point: a ledger claiming a token-by-token read of
a 5.5 MB append log would be the exact defect this audit exists to find.
