## 1 · substrate-gate on superbot-next: the ast.Num failure is now MEASURED in the venue

The phase-2 handoff was right that the merge measured nothing: `substrate-gate`
has **13** runs on `main`, newest **2026-07-17T09:19:13Z**, and the merge of
sbn #606 (`d5f66dc`, 2026-08-13T15:21Z) triggered no run. But the measurement
existed three commits away, on the PR's own branch:

- The gate ran **three times on `claude/substrate-kit-v1-21-0`** on 2026-08-13
  (14:54 / 15:04 / 15:17Z), all `completed failure` — the newest, run
  `31714594446` on head `8ac9c306`, four minutes before the merge.
- sbn #606 merged as a **squash** whose commit tree `8a18b731…` is
  **hash-identical** to that head's tree. Those three runs therefore executed
  on the exact tree `main` now holds — not merely on byte-identical product
  source.
- The failing step is the **pytest suite** (step 10), not the born-red hold:
  the substrate hygiene step passed (`check: all checks passed`) on the final
  head. Job `94495950779` log:
  `ERROR sb.counting.parsing:parsing.py:259 Error in safe_eval with expression
  '3+4': module 'ast' has no attribute 'Num'` →
  `FAILED tests/unit/band6/test_band6_message_games.py::test_parse_message_shapes
  - AssertionError: assert None == 7` → **1 failed, 3672 passed, 41 skipped**.
  Interpreter: `python-version: 3.x` resolved to **CPython 3.14.6**.
- The `isinstance(node, ast.Num)` site is `sb/domain/counting/parsing.py:307`
  at `main` (`# Python < 3.8 compat` — dead code on every interpreter `3.x`
  can resolve, and a crash on **3.14+**: `ast.Num` is deprecated since 3.8 and
  removed in 3.14, not 3.12 — CPython 3.12/3.13 still carry it with a
  DeprecationWarning, measured by Codex on this PR under 3.12.13). The phase-2 card's `:307` was correct;
  the handoff prompt drifted it to `:306`. (`:259` in the log is `safe_eval`'s
  error handler, which catches and logs the AttributeError.)
- Residual, stated: a *future* run's `3.x` could resolve differently; the
  break needs **3.14+** (corrected from "≥3.12" on Codex's measurement that
  3.12.13 still carries `ast.Num`), and `3.x` resolves 3.14+ today — a pin
  back to 3.12/3.13 would go green while the deprecation clock runs.

**Why the merge fired no run — CONFIRMED, no longer "plausibly".** The push
event for `d5f66dc` names actor **`github-actions[bot]`**: the enabler armed
native auto-merge with `GITHUB_TOKEN`
(sbn #606 `auto_merge.enabled_by: github-actions[bot]`, `merged_by:
github-actions[bot]`), and GitHub creates **no workflow runs for pushes
performed by that token** — `actions/runs?head_sha=d5f66dc…` returns
**0 runs of any workflow**, so this is repo-wide, not gate-specific. Same
pattern on the previous merge, sbn #602 (2026-08-05, also
`github-actions[bot]`): zero push runs; the nine runs carrying its SHA are all
`schedule` events (daily Postgres backup, weekly restore-verify — cron runs
record `main`'s head SHA). The 13 July push runs came from merges performed by
a **real user** — e.g. `a8ec5d78` *"coordinator close-out … — owner lands
(#503)"*, author `menno420`, committer `web-flow` — and real-user merges are
not suppressed. This is the third estate sighting of the same mechanism (the
roster deadlock, curious-research's silent pages stop); superbot's own
pre-regen enabler header documents it and uses `ROUTINE_PAT` for exactly this
reason.

**What this changes for the flagged owner decision** (make `substrate-gate`
required on superbot-next): required contexts are evaluated from
`pull_request` runs, which **do** fire — the suppression does not weaken the
required-check path; it only means post-merge `push` runs on `main` never
happen under bot-armed auto-merge. But making the gate required **today** reds
every PR at the pytest step until either the dead `ast.Num` branch is removed
or the gate pins the interpreter the product ships on (`ci.yml` pins 3.11).
The decision stays the owner's; it is now costed with a venue measurement
instead of a reasoned reproduction.

## 2 · superbot's shape: `init` works — the overclaim narrows, the decision stands

The phase-2 card recorded *"neither documented path fits"* after running
`status`, `upgrade` and `adopt` — but **both refusals literally said
"(run init first)"** and `init` was never run. Measured on a throwaway clone
of superbot at `5989b4f1` (the pre-#2436 parent), with the v1.21.0 dist as
`bootstrap.py.new` (sha256 `8807a00e…` = the released asset), never pushed:

- `status` and `upgrade` refuse exactly as recorded (exit 1,
  `no state at <root> (run init first)`, tree untouched).
- **`init` succeeds**: exit 0, creates exactly **one path** —
  `.substrate/state.json` — reusing the existing `project_id` from
  `substrate.config.json`. Pin untouched, nothing planted.
- **`init` unlocks `upgrade`**, which then runs (exit 0) and reproduces the
  over-correction class that disqualified `adopt`: **20 paths** touched,
  `docs/decisions.md` planted **beside superbot's existing `docs/decisions/`
  directory**, `CONSTITUTION.md`/`docs/CAPABILITIES.md`/`control/README.md`
  et al. planted, `substrate.config.json` rewritten (including the
  `{claim/*, claude/*}` automerge block — the advisory the phase-2 card
  re-attributed to superbot, here reproduced), and
  `.github/workflows/auto-merge-enabler.yml` **regenerated** — the kit's own
  carve-out scan flagged the host-added *"Enable native auto-merge (merge
  commit)"* step as NOT carried over and banked the pre-regen file. On the
  frozen oracle that regen is a live merge-machinery change, which the
  phase-2 constraint (docs-only, zero behaviour change) forbade.
- **Even then, no dist is vendored**: `bootstrap.py.new` is left unconsumed
  and no `bootstrap.py` appears at root — on the no-prior-dist shape, nothing
  in `init → upgrade` installs the dist the registry's primary-truth column
  reads.

**The corrected claim, narrowed rather than swapped** (the sb #2436 doctrine):
the kit **does** have a documented command sequence for this shape —
`init → upgrade` — so *"no command for that shape"* was an overclaim measured
over three commands with the recommended fourth untried. What remains true,
and is now `MEASURED` rather than inferred: **no kit path produces the
minimal, docs-only change superbot needed**, and the documented path does not
even vendor the dist. Vendor-the-dist + bump-the-pin stands as the right call,
on measured ground. The phase-2 card is annotated in place at the claim.
