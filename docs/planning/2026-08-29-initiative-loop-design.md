## What the owner decided, in his words

**Initiative is engineered output, not disposition.** *"What I think
initiative should mean is that agents act on what they see… when they notice
something that isn't done efficiently, or when certain things go wrong, that
they try to come up with a method to help the next session prevent that."*
And the mechanism: *"At the end of each session or after completing the main
objective, a hook should probably trigger a skill. That skill should define
'initiative' in such a way that it's a measurable thing… a few steps which
the agent takes to find out if anything it encountered in it's session fits
certain criteria, like if the repo isn't in an optimal state, o[r] if they
find conflicts or contradictory documents. Or if they have encountered
something that went wrong and can possibly be prevented the next time by
making a hook or a skill that forces the next agent to do things in a
structured predefined way."*

## The design

**Production (end of session / after the main objective).** A hook triggers
the initiative skill. The skill does not open with a question — self-report
is the prose-demand form the genesis dig showed dying while gated practices
held. It runs **mechanical detectors first**, producing a candidate list the
agent must disposition one by one: `[acted]` / `[proposed]` (a concrete
checker/hook/skill for a later session) / `[dismissed]` with a reason.
Initiative becomes countable — candidates raised vs. dispositions given —
and its red is visible: an empty disposition list while detectors raised
candidates. The candidate list is capped (top ~3) so the disposition step
stays a judgment, not a chore.

Detector list (each mechanical, each reading evidence that already exists):
1. **Contradiction sniff** — for every decision id or dated claim the
   session edited, grep its other appearances for stale citations. (The
   same-night Gemini-route capture over-revoking the paid-key spend decision
   — the fm #981 review round — was exactly this class, caught by an outside
   reviewer four files away.)
2. **Advisory delta** — did any gate advisory class grow this session?
3. **Guard-fire pattern** — a guard firing repeatedly on the same rule means
   a hook kept correcting the agent; candidate for making it structural.
4. **The session's own friction log** — the card's near-miss/retry record
   (conflicts, checker surprises, wrong-path probes), made a read field.
5. **Consumption check** — did this session disposition its predecessor's
   queued ideas? (The detector that keeps the loop from going write-only.)
6. **Repo-optimal residue** — conflict markers, dead links in touched
   files, a stale NOW pointer; mostly existing gate territory, routed into
   the disposition list instead of accumulating as advisories.

**The queue (one home — extend, don't invent).** The weighing step needs one
enumerable surface, and a floor already exists:
[`idea-backlog.md`](idea-backlog.md), generated by
`scripts/gen_idea_backlog.py` — which harvests **only the `- 💡` bullet
form** (`BULLET_RE`, script line 70, read); audit D36 (2026-08-11) already measured that the heading form is the
unharvested majority, and as of 2026-08-29 that majority is **382 of 449
card files** carrying a `💡 Session idea` heading (`grep -l` over
`.sessions/`). So the queue home is the existing generated backlog with its
harvester extended to the heading form, plus per-entry **stable slugs and a
disposition column**. The initiative skill appends in the harvestable form;
everything else points.

**Retirement rule (owner-agreed):** any session may retire a queued idea
**with a stated reason recorded in the queue itself**; the owner spot-checks
the kill column rather than approving each kill. Wrong kills are recoverable
because the kill is a record — the verification-over-capability thesis
applied to the queue's lifecycle.

**Consumption (the continuation-prompt step).** When a session writes a
handoff prompt, it reads the queue and weighs each live idea against the
task the owner asked the prompt to carry. Stated criteria for an idea to
join or outrank the task: it would prevent errors *in that task itself*; it
is small and genuinely ready (the [D-0022] carve-out test); or the task
matches it. The emitted prompt MUST carry a visible disposition line —
*"queue: N considered; carried a, deferred b because…"* — which is the
mechanism's falsifiable red: a continuation prompt written while live ideas
exist, with no disposition line, is a countable failure. Deference bias (the
owner's task always winning silently) is the expected failure mode; the
disposition line is what makes starvation visible.

**First-use test at birth (for everything tier (c) auto-builds).** The
fleet-preflight lesson in corrected form: the risk of auto-building is not
missing authorization — the owner asked for that skill, and the fleet
session that built it was well placed to — it is missing **validation**. It
was validated only backwards and never run (the 2026-08-29 dissection,
`../findings/2026-08-29-fleet-preflight-dissection.md`). So every auto-built
checker or surfacing hook names, at birth, the moment it fires next and what
its red looks like, making "never ran" visible within a session or two.
